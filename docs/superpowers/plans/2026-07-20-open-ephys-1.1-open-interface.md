# Open Ephys 1.0.x to 1.1 Open Interface Improvement Implementation Plan

> **Roadmap index:** Do not implement this document as one branch or one PR. Each change unit requires its own short plan under `docs/superpowers/plans/`, one narrow PR, and an independent release decision following `docs/superpowers/specs/2026-07-20-small-pr-release-policy.md`. The first executable plan is `2026-07-20-open-ephys-1.0.3-message-length-fix.md`.

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Improve official Open Ephys GUI v1.0.2 through incremental open-source `1.0.x` releases, then move to the local 1.1 line after adopting the official upstream 1.1 baseline. Fix build/test/API/accessibility defects, expand verification, publish the existing API accurately, and expose existing GUI behavior consistently without adding instrument features.

**Architecture:** Work from the verified v1.0.2 baseline in strict stages: test infrastructure first, semantic GUI/UIA metadata second, existing API documentation and correctness third, and additional HTTP aliases/discovery for existing behavior last. Preserve all legacy routes and invoke the same commands, parameters, actions, and accessibility handlers used by v1.0.2.

**Tech Stack:** C++17, JUCE 8, CMake, Ninja, GoogleTest, cpp-httplib, nlohmann/json, Windows UI Automation, PowerShell 7.

## Global Constraints

- Baseline commit is `c91afebcfb0678a667fb93f6312ed33c56ec640f`.
- First working release version is `1.0.3`; later releases increment `1.0.x`. No lab, organization, machine, or agent suffix. Recheck upstream before every release and never reuse an upstream version identifier.
- Preserve GPLv3 notices and keep all changes suitable for a public repository and upstream review.
- Do not add a processor, processing algorithm, acquisition mode, recording mode, plugin action, workflow engine, embedded agent, or coordinate automation.
- Keep plugin API `10`, third-party plugin ABI, XML configuration format, port `37497`, and legacy API routes compatible.
- Correct HTTP aliases may be added only for operations already available in v1.0.2.
- All GUI/API actions reuse existing v1.0.2 implementations.
- All JUCE UI access from HTTP handlers occurs on the message thread.
- Each task starts with a failing test or verifier, produces one reviewable change, and ends with a commit.
- Do not change `GUI_VERSION` from `1.0.2` until the first release task. Each release changes it only to the next verified, unused `1.0.x` number.
- Do not begin the local 1.1 line until the official upstream 1.1 release has been fetched, rebuilt, compared, and accepted as the new baseline.
- Use `docs/agent-api/upstream-issue-triage-2026-07-20.md` as the initial defect backlog. Prefer reviewed minimal backports of confirmed upstream fixes, each with regression coverage, and do not merge the feature-bearing upstream `development` branch wholesale.

Release batches are initially planned as `1.0.3` for baseline/test/P0 fixes, `1.0.4` for confirmed regressions and UIA metadata, `1.0.5` for existing HTTP API publication and hardening, and later `1.0.x` releases for aliases, semantic parity, and additional verified fixes. A batch may move only when its tests and compatibility evidence move with it.
