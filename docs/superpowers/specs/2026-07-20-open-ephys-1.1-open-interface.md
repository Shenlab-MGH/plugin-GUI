# Open Ephys GUI 1.0.x to 1.1 Open Interface Improvement Specification

**Status:** Ready for review

**Date:** 2026-07-20

**Baseline:** Official Open Ephys GUI v1.0.2, commit `c91afebcfb0678a667fb93f6312ed33c56ec640f`

**First working target:** Open Ephys GUI `1.0.3`, followed by incremental `1.0.x` releases until the upstream 1.1 baseline is available

## 1. Intent

This is an open-source improvement line built directly on official v1.0.2. Initial releases remain on `1.0.x`; the project moves to its `1.1` line only after the official upstream 1.1 release has been compared and adopted as the new baseline. It does not add new neuroscience, acquisition, recording, processing, visualization, or workflow capabilities.

The release improves what v1.0.2 already has:

1. make the official source build reproducibly on Windows;
2. fix defects in the build, tests, accessibility metadata, and HTTP control layer;
3. add stronger unit, integration, GUI, UI Automation, and API tests;
4. publish accurate documentation and schemas for the existing HTTP API;
5. give existing GUI controls stable labels, meanings, and automation identities;
6. expose existing behavior through consistent GUI, Windows UIA, and API bindings;
7. add correct HTTP routes or method aliases only when they invoke behavior already present in v1.0.2.

The project remains a normal open-source Open Ephys fork, not a Shen Lab-branded private build. Source, tests, scripts, specifications, and verification evidence are committed under the repository's existing GPLv3 terms.

## 2. Product Boundary

### Allowed

- build-system and test-harness fixes;
- bug fixes that restore intended v1.0.2 behavior;
- stable component IDs and accessibility metadata;
- correct Windows UI Automation exposure;
- HTTP validation, response, threading, and route correctness fixes;
- OpenAPI documentation for existing routes;
- new HTTP `POST`, `PUT`, `DELETE`, or discovery aliases for existing operations;
- semantic GUI/API mappings;
- regression tests and verification tools;
- documentation and examples.

### Not allowed in this improvement line

- a new processor or signal-processing algorithm;
- a new acquisition or recording mode;
- a new plugin action that is not already available in v1.0.2;
- an embedded agent, LLM, VLM, planner, or workflow engine;
- coordinate-click automation inside Open Ephys;
- a new plugin ABI;
- a new configuration format;
- lab-specific paths, tokens, names, hardware assumptions, or branding;
- removing or silently changing a working legacy API route.

## 3. Release Naming and Open-Source Policy

The first requested working release version is:

```text
1.0.3
```

Subsequent releases use the next available `1.0.x` patch number. There is no `shenlab`, organization, machine, or agent suffix in the product version.

Before every public package, check upstream releases and tags to ensure the selected `1.0.x` number is unused. Upstream has already set its `development` branch to `1.1.0`. Once official upstream 1.1 is published, freeze new 1.0.x work, compare and rebuild that official release, then establish the local 1.1 baseline. Do not publish a distinct binary under a version already assigned upstream.

Repository policy:

- preserve upstream copyright and GPLv3 notices;
- keep changes portable across supported Open Ephys platforms unless a file is explicitly Windows-specific;
- isolate the narrow Windows UIA bridge change under JUCE's Windows accessibility implementation;
- avoid proprietary runtime dependencies;
- document behavior so changes can be reviewed or proposed upstream;
- keep commits small enough for public code review.

## 4. Verified v1.0.2 Baseline

The local baseline is already established:

- `HEAD`, `origin/main`, and upstream tag `v1.0.2` resolve to `c91afebcfb0678a667fb93f6312ed33c56ec640f`;
- Release configuration and build succeed with CMake and Ninja;
- `open-ephys.exe` and all nine bundled plugin DLLs build;
- the rebuilt executable reports v1.0.2;
- imported Windows dependencies match the official release;
- each bundled plugin export count matches the official counterpart;
- supported unit tests pass;
- rebuilt and official GUIs launch with the File Reader configuration and show the same state.

Hardware acquisition and recording have not yet been proven locally and must remain labeled `hardware-required`.

## 5. Work Order

The order is deliberate. API expansion does not begin until the build and test baseline is reliable.

Suggested release slicing:

- `1.0.3`: reproducible build/test hardening and narrowly reviewed P0 upstream bug fixes;
- `1.0.4`: remaining confirmed regressions plus GUI labels, accessibility metadata, and Windows UIA identity;
- `1.0.5`: complete publication and hardening of the existing v1.0.2 HTTP API;
- later `1.0.x`: conventional aliases, semantic discovery, parity tests, and further confirmed bug fixes, each without new instrument behavior;
- local `1.1`: begins only after the official upstream 1.1 release becomes the rebuilt and verified baseline.

The exact patch allocation can shrink or expand based on verification results, but a patch release must contain only completed, tested work.

### Stage A — Build and test hardening

- preserve a clean, repeatable v1.0.2-equivalent build command;
- remove hardcoded test assumptions about repository folder name and Visual Studio output layout;
- prevent unit tests from loading unrelated user-installed plugins;
- repair RecordNode and ProcessorGraph test fixtures instead of hiding failures;
- add a baseline artifact comparison script;
- document which checks require hardware.

### Stage B — Existing GUI semantics and Windows UIA

- inventory meaningful controls;
- add stable, neutral IDs;
- replace ambiguous accessible names such as `R`, `+`, `-`, and `OFF` with their actual meaning;
- expose correct role, enabled state, selection/toggle state, supported actions, and values;
- preserve visible text, layout, callbacks, and user behavior;
- verify with Windows UI Automation directly.

### Stage C — Existing HTTP API publication and fixes

- write an OpenAPI 3.1 document for every existing v1.0.2 route;
- add tests for request parsing, validation, status codes, and response shapes;
- marshal GUI access safely to the JUCE message thread;
- fix incorrect plain-text errors and inconsistent failure codes without changing successful legacy responses;
- document remote-listening security characteristics without introducing a new security product feature in this release.

### Stage D — Additional API exposure for existing behavior

- add correct REST method aliases for existing operations;
- retain legacy routes for compatibility;
- add semantic GUI-control discovery;
- map existing GUI actions to existing commands, parameters, processor actions, or accessibility handlers;
- add only routes that expose an already-existing v1.0.2 behavior;
- test GUI action, UIA action, and API action equivalence.

### Stage E — 1.0.x release verification and later 1.1 baseline transition

- clean build;
- full supported test suite;
- nine bundled plugins;
- legacy API compatibility;
- OpenAPI conformance;
- GUI/UIA/API semantic parity;
- official v1.0.2 visual and binary-surface comparison;
- explicit hardware verification report.

## 6. Compatibility Requirements

- Plugin API remains `10`.
- Existing third-party plugins load without recompilation.
- XML configuration remains compatible.
- Port `37497` and HTTP server enable/disable behavior remain available.
- Every existing `/api/*` route remains callable with its v1.0.2 method.
- Successful legacy response bodies keep their existing keys and value meanings.
- Existing menu commands, shortcuts, button callbacks, parameter actions, ProcessorGraphActions, and UndoManager behavior remain in use.
- No API worker thread directly accesses or mutates JUCE UI state.
- Accessibility changes do not alter layout, focus order, visible text, rendering, or keyboard behavior unless a verified accessibility defect requires it.

## 7. Test-Harness Fixes

The current investigation identified three concrete harness defects.

### 7.1 Plugin path layout

`PluginManagerTests.cpp` assumes a Visual Studio multi-configuration directory layout. Tests must receive the plugin fixture path from CMake rather than derive it from executable location.

### 7.2 User plugin contamination

Tests can load `%LOCALAPPDATA%\Open Ephys\plugins-api...` when the checkout folder is not literally named `plugin-GUI\Build`. Tests must use an explicit isolated plugin search path and never inspect a developer's user plugin directory.

### 7.3 RecordNode application fixture

The test application omits `ControlPanel`, but RecordNode construction asks `CoreServices` for the default recording engine. The fixture must supply the same required application service or a test double; production RecordNode behavior must not be weakened to satisfy the test.

After these fixes, RecordNode and ProcessorGraph tests should run in the normal supported suite. Any remaining exclusion requires a specific documented technical reason.

## 8. GUI and UI Automation Semantics

Every meaningful control receives a stable ID:

```text
oe.<area>.<control>
```

Dynamic examples:

```text
oe.processor.<node_id>
oe.processor.<node_id>.parameter.<parameter_name>
oe.processor.<node_id>.stream.<stream_id>
oe.processor_catalog.<processor_slug>
```

The component receives:

- JUCE `ComponentID`;
- accessible title;
- description;
- help text where useful;
- correct accessible role;
- existing action and value patterns.

On Windows, the bundled JUCE UIA bridge currently synthesizes AutomationId from the title hierarchy. The narrow fix is:

- return a non-empty `ComponentID` as AutomationId;
- keep JUCE's existing fallback for components without an ID.

This is metadata exposure, not a new GUI capability.

## 9. Existing API Publication

The v1.0.2 routes to document and test include:

- `/api/config`;
- `/api/status`;
- `/api/cpu`;
- `/api/latency`;
- `/api/audio/devices`;
- `/api/audio/device` and `/api/audio`;
- `/api/recording` and `/api/recording/{processor_id}`;
- `/api/message`;
- `/api/load` and `/api/save`;
- `/api/processors/list`;
- `/api/processors` and processor detail routes;
- processor and stream parameter routes;
- processor config route;
- processor add/delete/clear routes;
- `/api/undo` and `/api/redo`;
- `/api/quit`.

The OpenAPI document describes actual v1.0.2 behavior first. It must not describe a planned route as implemented.

## 10. Correct Method Aliases

Some v1.0.2 mutations use `GET`. They remain for compatibility, but the improvement line may add conventional aliases:

```text
POST   /api/processors/clear
POST   /api/undo
POST   /api/redo
DELETE /api/processors/{id}
POST   /api/processors
POST   /api/messages
POST   /api/config/load
POST   /api/config/save
POST   /api/application/quit
```

Each alias must call the same existing implementation as its legacy route and return an equivalent resulting state. It must not create a new operation.

## 11. Semantic Control Publication

After GUI semantics are verified, add discovery routes:

```text
GET  /api/ui
GET  /api/ui/controls
GET  /api/ui/controls/{id}
POST /api/ui/controls/{id}/actions/{existing_action}
PUT  /api/ui/controls/{id}/value
```

The control record includes ID, label, description, role, enabled/visible state, current value, supported existing actions, and preferred model API binding.

Generic invocation is permitted only when the JUCE AccessibilityHandler already exposes that action. Generic value setting is permitted only when its existing AccessibilityValueInterface is writable.

If a stronger existing model route exists, the catalog points to it and the agent should prefer it.

## 12. Testing Layers

### Unit

- semantic ID validation and uniqueness;
- metadata application;
- accessibility snapshot serialization;
- request parsing and JSON errors;
- correct method alias dispatch;
- legacy response compatibility;
- message-thread execution;
- test plugin isolation.

### Application integration

- launch File Reader configuration;
- call every safe legacy read route;
- test safe mutations and restore state;
- validate OpenAPI against responses;
- compare GUI, UIA, and API state for representative controls;
- validate configuration load/save with temporary files.

### Binary/runtime regression

- build executable and nine plugins;
- compare imports and plugin exports with official v1.0.2;
- compare startup screenshots and responsiveness;
- record expected version/hash differences.

### Hardware

- acquisition start/stop;
- recording start/stop;
- recording file integrity;
- acquisition-board controls;
- hardware-plugin controls.

## 14. Acceptance Criteria

1. The first working product version is `1.0.3`; each public `1.0.x` identifier passes the upstream version-collision gate, and the project moves to 1.1 only after adopting the official upstream 1.1 baseline.
2. The project remains publicly buildable under its existing open-source license.
3. No new instrument or scientific feature is introduced.
4. A clean Windows build produces the executable and nine bundled plugins.
5. Test fixtures no longer depend on checkout folder name, developer plugins, or Visual Studio output layout.
6. RecordNode and ProcessorGraph tests run or have a newly proven, narrowly documented blocker.
7. Existing API routes have accurate OpenAPI documentation and regression coverage.
8. Correct method aliases call the same behavior as legacy routes.
9. Meaningful GUI controls expose stable, accurate Windows UIA metadata.
10. GUI, UIA, and API use the same control identity and meaning.
11. All supported tests pass.
12. Official v1.0.2 baseline behavior remains intact.
13. Hardware-dependent claims remain labeled until verified on hardware.
